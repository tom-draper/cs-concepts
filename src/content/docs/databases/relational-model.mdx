Early databases stored records linked by pointers. To find a customer's orders, a program started at the customer record and followed a chain to each order. The program had to know the exact layout. If the layout changed, or somebody asked a question the designers had not planned for, the programs had to be rewritten.

In 1970 Edgar Codd, a researcher at IBM, proposed something different. Store data in plain tables. Connect tables by values that match. Let users say what they want and leave it to the system to work out how to fetch it. This is the **relational model**.

## Tables

The model has one structure. A **relation** is a table with named columns, where every row has a value for each column.

| Formal term | Everyday term | Meaning |
| --- | --- | --- |
| Relation | table | a set of rows with the same columns |
| Tuple | row, record | one thing being described |
| Attribute | column, field | one property, with a name and a type |
| Domain | type | the set of values a column may hold |
| Schema | | the names and types of the columns |

Two rules separate a relation from a spreadsheet.

**Rows have no order.** A relation is a [set](/foundations/sets-and-relations/) of rows. There is no "first row" or "row 7". If you want a particular order, you ask for it in the query.

**Every cell holds one value.** There are no lists inside cells and no repeating groups of columns such as `phone1`, `phone2`, `phone3`. A customer with three phone numbers gets three rows in a separate table.

## Keys

With no row numbers and no pointers, a row is identified by its contents.

A **primary key** is a column, or a set of columns, whose value is different in every row. In `customers` it is `id`. No two customers share one, and none is missing, so `id = 3` names exactly one row.

A **foreign key** is a column that holds the primary key of a row in another table. In `orders`, the column `customer_id` says which customer placed the order. That shared value is the entire link between the two tables. Nothing is stored that physically joins them.

| | Primary key | Foreign key |
| --- | --- | --- |
| Purpose | identifies a row in its own table | refers to a row in another table |
| Must be unique | yes | no, many orders can name one customer |
| May be empty | no | sometimes |

Keys are often meaningless numbers generated by the database, called **surrogate keys**. A meaningful value such as an email address looks like a natural key until somebody changes theirs.

## Relationships

Foreign keys express how things relate.

| Relationship | Example | How it is stored |
| --- | --- | --- |
| One to many | a customer has many orders | a foreign key on the "many" side |
| One to one | a user has one profile | a foreign key that is also unique |
| Many to many | students take many courses, and courses have many students | a third table with one row for each pairing, holding two foreign keys |

The third case shows the model's habit of turning everything into a table. The relationship itself, "this student takes this course", becomes a row.

## Operations that return tables

Codd also defined a small set of operations, the **relational algebra**. Each takes one or two tables and produces a table.

| Operation | Does | In the widget above |
| --- | --- | --- |
| Selection | keeps the rows that satisfy a condition | "some rows" |
| Projection | keeps some of the columns | "some columns" |
| Join | combines rows from two tables where values match | see [joins](/databases/joins/) |
| Union, difference | set operations on rows | |
| Rename | changes column names | |

Because the result is always another table, operations can be chained without limit: select from a join of a projection. This property is called **closure**, and it is what makes a query language possible. [SQL](/databases/sql/) is, at heart, a notation for combining these operations.

## What, not how

The model's deepest idea is the separation of two levels.

| Logical level | Physical level |
| --- | --- |
| tables, columns, keys | files, pages, [indexes](/databases/indexes/), sort orders |
| what a query means | how it is carried out |
| fixed by the designer of the schema | chosen and changed by the database |

A query names tables and conditions. It does not mention files, pointers or loops. The database's [query planner](/databases/query-planning/) decides whether to use an index, in what order to join and which algorithm to use.

This is **data independence**. An index can be added, a table moved to faster storage or the whole engine replaced, and every existing query still works and returns the same answer, only faster or slower. Before the relational model, each of those changes meant editing application code.

## Constraints

A schema also states rules the data must always obey. The database rejects any change that would break one.

| Constraint | Guarantees |
| --- | --- |
| Type | a column of dates holds only dates |
| `NOT NULL` | the column always has a value |
| `UNIQUE` | no two rows share a value |
| `PRIMARY KEY` | unique and not null |
| `FOREIGN KEY` | the referenced row exists. This is **referential integrity** |
| `CHECK` | any condition, such as `amount >= 0` |

Putting rules in the database means they hold whichever application, script or person makes a change. An order can never refer to a customer who does not exist.

## Missing values

Sometimes a value is unknown or does not apply. The model's answer is **NULL**, a marker meaning "no value here". The last order in the widget has a NULL `customer_id`.

NULL is not zero and not an empty string, and it behaves unlike any value. Comparing anything with NULL gives neither true nor false but "unknown", so `customer_id = NULL` matches no rows, including the row where it is NULL. That surprises nearly everyone once. It is covered under [SQL](/databases/sql/#null).

## Why it won

| Strength | Why it matters |
| --- | --- |
| Any question can be asked | queries are not limited to the paths the designers anticipated |
| One copy of each fact | [normalised](/databases/normalisation/) tables cannot contradict themselves |
| Integrity enforced centrally | constraints hold for every program that uses the data |
| Mathematical foundation | queries can be rewritten into faster equivalent forms, provably without changing the result |
| Independence from storage | performance can be tuned without touching applications |

The first relational systems, in the late 1970s, were slower than their rivals, and critics doubted a system could choose access paths as well as a programmer. The optimisers improved, hardware got faster, and by the 1990s relational databases were the default for nearly everything.

## Where it strains

**Shapes that are not tables.** A deeply nested document or a [graph](/data-structures/graph-representations/) of friendships can be stored in tables, but querying it takes many joins. Document and graph databases store those shapes directly.

**Objects in programs.** Application code holds nested objects with references, and a database holds flat rows with keys. Translating between them is tedious, and the tools that automate it, object-relational mappers, hide costs that later surprise people.

**Rigid schemas.** Every row in a table has the same columns, and changing the schema of a large table needs care. Systems that accept any shape are easier to start with, and push the checking into application code.

**Scaling across machines.** Joins and [transactions](/databases/acid/) are simple on one machine and hard across many. The first wave of "NoSQL" systems gave them up for scale. Many later systems added them back.

In practice the boundaries have blurred. Relational databases now store JSON, and most other databases have grown query languages resembling SQL.

## Key takeaways

- The relational model represents all data as tables of rows with typed, named columns.
- Rows are unordered and identified by a primary key. Tables are connected by foreign keys holding matching values.
- A few operations on tables, such as selection, projection and join, each produce a table and so can be combined freely.
- Queries state what is wanted. The database chooses how, which lets storage and indexes change without breaking applications.
- Constraints in the schema keep the data valid whoever changes it.
- The model fits most structured data well and fits nested documents, graphs and very large distributed systems less comfortably.

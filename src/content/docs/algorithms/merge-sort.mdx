Merge sort starts from one observation: **merging two lists that are already sorted is easy**. Look at the front of each, take the smaller, and repeat. One pass and you are done.

So to sort an array, split it in half, sort each half, and merge them. How do you sort each half? The same way. Keep splitting until the pieces have one element each, and a one-element piece is already sorted.

Each element is looked at once, so merging n elements is O(n).

## The code

```python
def merge_sort(a):
    if len(a) <= 1:
        return a
    mid = len(a) // 2
    left = merge_sort(a[:mid])
    right = merge_sort(a[mid:])

    merged, i, j = [], 0, 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:      # <= keeps equal items in order
            merged.append(left[i])
            i += 1
        else:
            merged.append(right[j])
            j += 1
    return merged + left[i:] + right[j:]
```

This is [divide and conquer](/algorithms/divide-and-conquer/) in its purest form: divide the problem, solve the parts [recursively](/algorithms/recursion/), combine the answers.

## Why it is O(n log n)

Picture the work in layers.

| Layer | Pieces | Size of each | Total merge work |
| --- | --- | --- | --- |
| Top | 1 | n | n |
| Next | 2 | n / 2 | n |
| Next | 4 | n / 4 | n |
| … | … | … | n |
| Bottom | n | 1 | n |

Every layer does about n work in total, because every element is merged once per layer. And halving n until it reaches 1 takes log₂ n layers. Multiply: **n log₂ n**.

For a million elements that is about 20 million operations, against about 500 billion for an O(n²) sort.

## Strengths and weaknesses

**Guaranteed performance.** There is no bad input. [Quicksort](/algorithms/quicksort/) is usually faster but can degrade to O(n²); merge sort cannot.

**Stable.** Equal elements keep their original order, which matters when sorting records by one field.

**Works on sequential data.** Merging only ever reads forwards, so merge sort is the natural way to sort a [linked list](/data-structures/linked-lists/), where it needs no extra memory at all. It is also how you sort data too big for memory: sort chunks that fit, write them to disk, then merge the files. That is *external sorting*, and databases depend on it.

**Parallelises well.** The two halves are independent and can be sorted on different cores.

**Needs extra memory.** The O(n) buffer is its main cost for arrays, and the copying makes it slower than quicksort in practice when memory is tight.

## In the wild

**Timsort**, the sort built into Python and used by Java for objects, is a merge sort tuned for real data. It looks for runs that are *already* sorted, extends short ones with [insertion sort](/algorithms/insertion-sort/), and merges the runs. On data with existing order, which is common, it approaches O(n).

Whenever a library documents its sort as stable, there is almost certainly a merge sort inside.

## Key takeaways

- Merge sort splits the array in half, sorts each half recursively, and merges the results.
- Merging two sorted runs takes one linear pass.
- It is O(n log n) in every case: log n layers, each doing n work.
- It is stable and predictable, but needs O(n) extra memory for arrays.
- It suits linked lists, external sorting and any situation needing a stable sort.

A plain [binary search tree](/data-structures/binary-search-trees/) is only fast if it happens to be well-shaped. Feed it sorted keys and it degrades into a linked list with O(n) operations. The AVL tree was the first structure to fix this, in 1962. It is named after its inventors, Georgy Adelson-Velsky and Evgenii Landis.

The idea: after every insert or delete, check whether any node has become lopsided, and if so, repair it locally with a **rotation**.

## The balance rule

Define the **height** of a node as the number of nodes on the longest path from it down to a leaf, and its **balance factor** as:

```text
balance factor = height of left subtree − height of right subtree
```

An AVL tree is a binary search tree in which **every node's balance factor is −1, 0 or +1**. The two sides of any node may differ in height by at most one.

This is a strict rule. It keeps the height of a tree with n keys below about 1.44 × log₂ n, so even the worst-shaped AVL tree is only modestly taller than a perfect one. A million keys never need more than about 29 levels.

## Rotations

A rotation rearranges three links to change which of two nodes is the parent, **without breaking the search tree ordering**. It is the basic move behind every self-balancing binary tree.

Read the keys left to right before and after: `5 10 20 25 30 40` both times. The rotation changed the shape and nothing else. It also touched only a constant number of pointers, so it is O(1).

A **left rotation** is the mirror image, used when the right side is too tall.

```python
def rotate_right(y):
    x = y.left
    y.left = x.right    # x's right subtree changes parent
    x.right = y
    update(y)           # recompute heights, lower node first
    update(x)
    return x            # x is the new root of this subtree
```

## The four cases

When a node goes out of balance, the fix depends on *where* the extra height is. There are four shapes, in two mirrored pairs.

### Outside cases: one rotation

The extra height is on the outer edge: the left child's left side, or the right child's right side. A single rotation fixes it. Inserting `10, 20, 30` in order produces the simplest example:

### Inside cases: two rotations

The extra height is on the inner side, forming a zig-zag. A single rotation would just flip the zig-zag to lean the other way. So first rotate the child to straighten it into an outside case, then rotate the parent. Inserting `30, 10, 20`:

| Unbalanced node is | Child leans | Case | Fix |
| --- | --- | --- | --- |
| Left-heavy (+2) | left or level | Left-left | Rotate right |
| Left-heavy (+2) | right | Left-right | Rotate child left, then rotate right |
| Right-heavy (−2) | right or level | Right-right | Rotate left |
| Right-heavy (−2) | left | Right-left | Rotate child right, then rotate left |

## Putting it together

Each node stores its height. An insert is an ordinary BST insert, followed by a rebalance at every node on the way back up to the root.

```python
def height(node):
    return node.height if node else 0

def update(node):
    node.height = 1 + max(height(node.left), height(node.right))

def balance(node):
    return height(node.left) - height(node.right)

def rebalance(node):
    update(node)
    if balance(node) > 1:                    # left-heavy
        if balance(node.left) < 0:           # left-right case
            node.left = rotate_left(node.left)
        return rotate_right(node)
    if balance(node) < -1:                   # right-heavy
        if balance(node.right) > 0:          # right-left case
            node.right = rotate_right(node.right)
        return rotate_left(node)
    return node

def insert(node, key):
    if node is None:
        return Node(key)                     # a new node has height 1
    if key < node.key:
        node.left = insert(node.left, key)
    elif key > node.key:
        node.right = insert(node.right, key)
    return rebalance(node)
```

An insertion needs at most one fix (a single or double rotation); once the lowest unbalanced node is repaired, everything above it is back in balance too. A deletion can need a rotation at every level on the way up, which is still only O(log n).

Unlike a plain BST, these are **worst-case** guarantees. No sequence of operations can make an AVL tree slow.

## AVL or red-black?

The main alternative is the [red-black tree](/data-structures/red-black-trees/), which enforces a looser balance rule.

| | AVL tree | Red-black tree |
| --- | --- | --- |
| Maximum height | about 1.44 log₂ n | about 2 log₂ n |
| Lookups | slightly faster (shallower) | slightly slower |
| Inserts and deletes | more rotations | fewer rotations |
| Typical use | read-heavy workloads | general-purpose library maps |

The difference is a constant factor either way. Most standard libraries chose red-black trees; AVL trees are a good fit when lookups heavily outnumber updates. For data that lives on disk, both lose to the [B-tree](/data-structures/b-trees/).

## Key takeaways

- An AVL tree is a BST in which the two subtrees of every node differ in height by at most one.
- That rule caps the height at about 1.44 log₂ n, making search, insert and delete O(log n) in the worst case.
- Balance is restored with rotations, which reshape the tree in O(1) while preserving key order.
- Outside cases need one rotation; inside (zig-zag) cases need two.

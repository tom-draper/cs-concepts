[Binary search](/algorithms/binary-search/) finds anything in a sorted [array](/data-structures/arrays/) in O(log n). But keeping an array sorted is expensive: every insertion shifts elements, which is O(n). A binary search tree (BST) keeps the halving and drops the shifting, by storing the data as linked nodes instead of a contiguous block.

## The one rule

Each node holds a key and has up to two children, left and right. The whole structure rests on a single invariant:

> For every node, all keys in its **left** subtree are smaller, and all keys in its **right** subtree are larger.

<Tree
  root={{ k: 8, c: [{ k: 3, c: [1, { k: 6, c: [4, 7] }] }, { k: 10, c: [null, { k: 14, c: [13, null] }] }] }}
  caption="Pick any node: everything below it to the left is smaller, everything to the right is larger."
/>

The rule applies to whole subtrees, not just direct children. `7` sits in the left subtree of `8`, so it must be smaller than 8, even though it is three levels down.

## Searching

Start at the root and compare. If the target is smaller, go left; if larger, go right. Each step discards an entire subtree. Here is the path to **7**:

<Tree
  root={{ k: 8, c: [{ k: 3, c: [1, { k: 6, c: [4, 7] }] }, { k: 10, c: [null, { k: 14, c: [13, null] }] }] }}
  highlight={[8, 3, 6]}
  alt={[7]}
  caption="7 is less than 8, so go left. More than 3, go right. More than 6, go right. Found."
/>

Four nodes examined out of nine. If you fall off the bottom of the tree, the key is not there.

```python
class Node:
    def __init__(self, key):
        self.key = key
        self.left = None
        self.right = None


def search(node, key):
    while node is not None and node.key != key:
        node = node.left if key < node.key else node.right
    return node
```

## Inserting

Inserting is a search that expects to fail. Walk down as if looking for the key, and attach a new node at the empty spot where the search falls off. Inserting **5**:

<Tree
  root={{ k: 8, c: [{ k: 3, c: [1, { k: 6, c: [{ k: 4, c: [null, 5] }, 7] }] }, { k: 10, c: [null, { k: 14, c: [13, null] }] }] }}
  highlight={[8, 3, 6, 4]}
  alt={[5]}
  caption="Left of 8, right of 3, left of 6, right of 4. The new node always becomes a leaf."
/>

Nothing else in the tree moves. Compare that with a sorted array, where the same insertion would shift every element after it.

```python
def insert(node, key):
    if node is None:
        return Node(key)
    if key < node.key:
        node.left = insert(node.left, key)
    elif key > node.key:
        node.right = insert(node.right, key)
    return node
```

## Deleting

Removing a node has three cases, in increasing order of awkwardness.

1. **A leaf**: just remove it.
2. **One child**: replace the node with its child.
3. **Two children**: this node is holding two subtrees apart, so something must take its place. Use its **in-order successor**, the smallest key in its right subtree. That key is larger than everything on the left and smaller than everything else on the right, so the invariant survives.

Deleting **3** from the original tree is the third case. Its successor is `4`:

## Sorted order for free

Visit the left subtree, then the node, then the right subtree, recursively. This **in-order traversal** produces the keys in ascending order: `1 3 4 6 7 8 10 13 14`.

```python
def in_order(node):
    if node is not None:
        yield from in_order(node.left)
        yield node.key
        yield from in_order(node.right)
```

This is what a BST can do that a [hash table](/data-structures/hash-tables/) cannot. Because the keys are ordered, a BST can efficiently answer "what is the smallest key?", "what comes after 6?" and "give me everything between 4 and 10".

## The catch: shape depends on insertion order

Every operation walks from the root towards a leaf, so the cost is the **height** of the tree. A well-shaped tree with n keys has a height of about log₂ n. But nothing in the rule forces a good shape. Insert keys that are already sorted, `1, 2, 3, 4, 5`, and each one goes to the right of the last:

## Self-balancing trees

The fix is to rearrange the tree during inserts and deletes so its height stays close to log n whatever order the keys arrive in. These **self-balancing** trees are what libraries actually ship.

- **[AVL trees](/data-structures/avl-trees/)** keep the two subtrees of every node within one level of each other. Strictly balanced, so lookups are fast.
- **[Red-black trees](/data-structures/red-black-trees/)** allow a looser balance in exchange for less rearranging on writes. They back `TreeMap` in Java and `std::map` in C++.
- **[B-trees](/data-structures/b-trees/)** put many keys in each node to keep the tree very shallow. They are the standard for databases and filesystems.

## Key takeaways

- The invariant: smaller keys to the left, larger to the right, at every node.
- Search, insert and delete each follow one path from the root, so they cost the tree's height.
- An in-order traversal yields the keys sorted, which enables range and nearest-key queries.
- A plain BST can degrade to O(n). Production code uses a self-balancing variant.

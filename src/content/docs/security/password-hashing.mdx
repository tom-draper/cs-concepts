Every service that takes a password has to check it at the next login, so it has to keep something. What it keeps decides how bad a breach is.

Assume the database will leak. Backups get misplaced, an [injection](/security/injection-attacks/) bug dumps a table, an employee copies a file. The design goal is that the leaked file is as useless as possible.

## What not to store

**The password.** A leak hands over every account at once. People reuse passwords, so it hands over their email and bank accounts too.

**The password, encrypted.** The server needs the key to check logins, so the key sits next to the data and leaks with it.

**A fast hash of the password.** This is the instructive mistake. A [cryptographic hash](/security/cryptographic-hash-functions/) cannot be reversed, so storing SHA-256 of the password looks safe. To check a login, hash what was typed and compare.

The flaw is that passwords are not random. An attacker does not reverse the hash. They guess: hash a likely password, look for it in the leaked table, and repeat. SHA-256 was designed to be fast, and a rack of graphics cards computes around ten billion of them a second.

Two things stand out in the table. Length beats cleverness, since each extra character multiplies the search. And the choice of hash moves every row by a factor of a million.

## Salts

The widget's lower table shows two users with the same password.

Without a salt, their stored hashes are identical. An attacker sees at once which accounts share a password, and cracking one cracks all of them. Worse, the attacker can do the work before the breach. A **rainbow table** is a precomputed map from hashes back to passwords, built once and reused against every database that used the same hash.

A **salt** is a random value, different for every user, hashed along with the password and stored beside the result.

```
stored = salt, hash(salt + password)
```

The salt is not secret. Its job is to make every user's hash a different function. Now equal passwords give unrelated hashes, a precomputed table would need to cover every possible salt, and each guess the attacker makes tests one user instead of all of them. Against a million users, that alone slows the attack a million times.

Sixteen random bytes per user is the usual size. Generate a new one whenever the password changes.

## Slow on purpose

A salt does not help a user whose password is weak, because the attacker can still guess at that one account at full speed. The second defence is to make each guess expensive.

A **password hashing function** is built to take a chosen amount of time and memory. A login costs the server perhaps 100 milliseconds, which nobody notices. An attacker who needs billions of guesses pays that billions of times.

| Function | Cost is tunable in | Notes |
| --- | --- | --- |
| PBKDF2 | time | Repeats HMAC many thousands of times. Old, and cheap to run on graphics cards. |
| bcrypt | time | From 1999 and still sound. Ignores input beyond 72 bytes. |
| scrypt | time and memory | The first widely used memory-hard design. |
| Argon2id | time, memory and threads | Winner of a public competition in 2015. The current recommendation. |

**Memory hardness** is the important advance. A function that only costs time can be run thousands of times in parallel on a graphics card or a custom chip, which is far cheaper per guess than the server's processor. A function that needs 64 MB for each guess cannot, because the memory is what limits how many guesses fit on the chip.

The cost setting is called the **work factor**. It is stored with the hash, so it can be raised as hardware improves. When a user logs in with a hash made under an old setting, the server has the password in hand for a moment and can rehash it under the new one.

<Aside title="Peppers">

A **pepper** is one more secret mixed into every hash, the same for all users, kept outside the database in a key management service or hardware module. If only the database leaks, the attacker cannot test any guess at all. It adds to salting and slow hashing and does not replace them.

</Aside>

## Checking a login

The stored string holds everything needed to check a password: the algorithm, its settings, the salt and the result.

```
$argon2id$v=19$m=65536,t=3,p=4$c29tZXNhbHQ$RdescudvJCsgt3ub+b+dWRWJTmaaJObG
 algorithm      memory, passes,  salt        hash
                threads
```

To verify, the server reads the settings and salt from the stored string, hashes the submitted password the same way, and compares the results in constant time.

Around that sit the online defences. Limit attempts per account and per address, so that guessing through the login form is thousands of times slower than guessing against a stolen file. Give the same error for an unknown user and a wrong password. And hash a dummy value when the user does not exist, so that response time does not reveal which names are registered.

The cost falls on the defender as well. A login endpoint that burns 100 ms of processor and 64 MB of memory per request can be flooded, so it needs rate limiting in front of it.

## Implementation

Python's standard library includes scrypt.

```python
import hashlib, hmac, os

def hash_password(password):
    salt = os.urandom(16)
    key = hashlib.scrypt(password.encode(), salt=salt, n=2**14, r=8, p=1)
    return salt + key

def check_password(password, stored):
    salt, key = stored[:16], stored[16:]
    attempt = hashlib.scrypt(password.encode(), salt=salt, n=2**14, r=8, p=1)
    return hmac.compare_digest(attempt, key)

stored = hash_password('correct horse')
check_password('correct horse', stored)      # True
check_password('correct house', stored)      # False
hash_password('correct horse') == stored     # False, the salt differs
```

In an application, use the framework's password API or an Argon2 library, which also handle the encoding and the upgrade of old hashes.

## Beyond the hash

Hashing limits the damage of one kind of failure. It does nothing about the others.

**Credential stuffing.** Attackers take name and password pairs leaked from one site and try them on others. The best hash in the world does not help if the password is already public. Checking new passwords against lists of breached ones does.

**Phishing.** A user who types their password into a fake page has given it away in plaintext.

**Composition rules.** Forcing symbols and regular changes produces `Password1!` followed by `Password2!`. Current guidance is to require length, allow anything including spaces, block known-breached passwords, and force a change only after a compromise.

The stronger fixes move away from shared secrets. A password manager gives every site a long random password. A second factor makes a stolen password insufficient. [Passkeys](/security/authentication/#passkeys) leave the server holding only a public key, which is worthless to a thief.

## Key takeaways

- Store a salted, slow hash of each password. Never the password, and never a plain fast hash.
- Attackers guess passwords and hash the guesses. The defence is to make each guess cost as much as possible.
- A unique random salt per user makes equal passwords look different and defeats precomputed tables.
- Use Argon2id, or scrypt or bcrypt, with a work factor tuned to about a tenth of a second.
- Memory-hard functions blunt the advantage of graphics cards and custom chips.
- Length matters more than character variety, and no hash protects a password that is reused or phished.

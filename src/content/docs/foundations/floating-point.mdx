Type `0.1 + 0.2` into almost any programming language and you get:

```text
0.30000000000000004
```

This is not a bug in the language, and it is the same everywhere. It is a consequence of how computers represent numbers that are not whole. Understanding it takes about ten minutes and will save you from a whole category of mistakes.

## Scientific notation, in binary

Scientists write very large and very small numbers in a compact form: 6.02 × 10²³, or 1.6 × 10⁻¹⁹. There are three parts: a sign, some significant digits, and an exponent saying where the decimal point goes.

**Floating point** is the same idea in base 2. A number is stored as three fields.

- **Sign**: one bit. 0 for positive, 1 for negative.
- **Exponent**: which power of two to scale by.
- **Fraction**: the significant binary digits.

The point "floats" because the exponent can place it anywhere, which is what lets one format hold both the size of an atom and the distance between galaxies.

The format is fixed by a standard, IEEE 754, which virtually all hardware follows. Its two common sizes:

| | Bits | Sign | Exponent | Fraction | Precision | Largest value |
| --- | --- | --- | --- | --- | --- | --- |
| Single (`float`) | 32 | 1 | 8 | 23 | about 7 decimal digits | about 3.4 × 10³⁸ |
| Double (`double`) | 64 | 1 | 11 | 52 | about 15–16 decimal digits | about 1.8 × 10³⁰⁸ |

Python's `float` and JavaScript's `number` are doubles.

- **1e39** is too big for the format and becomes infinity.

## Why 0.1 cannot be stored

In decimal, some fractions never end: 1/3 is 0.3333… forever. You can write it to any number of places, but never exactly.

Binary has the same problem with different fractions. A fraction has a finite binary form only if its denominator is a power of two. So 1/2, 1/4 and 5/8 are exact. But 1/10 is not, because 10 has a factor of 5. In binary it is:

```text
0.0001100110011001100110011...   (the pattern 0011 repeats forever)
```

The format has only a fixed number of fraction bits, so the pattern is cut off and rounded. What gets stored is the nearest representable value, which is very slightly different from 0.1.

The same happens to 0.2 and to 0.3. When you add the stored versions of 0.1 and 0.2, the small errors do not cancel, and the result is not quite the stored version of 0.3.

## Living with it

### Do not compare with ==

```python
0.1 + 0.2 == 0.3                    # False
abs((0.1 + 0.2) - 0.3) < 1e-9       # True: compare within a tolerance
```

Ask whether two values are *close enough*, not whether they are identical. Most languages have a helper, such as `math.isclose` in Python.

### Do not use it for money

Rounding errors that are invisible in a physics simulation are unacceptable in a bank balance. Store money as a **whole number of the smallest unit** (cents, pence), or use a decimal type designed for it.

### Large whole numbers lose precision too

A float has a fixed number of significant bits. Once a number is big enough, there are not enough bits left to distinguish neighbouring integers.

| Format | Every whole number is exact up to |
| --- | --- |
| Single | 16,777,216 (2²⁴) |
| Double | 9,007,199,254,740,992 (2⁵³) |

Beyond that, representable values are 2 apart, then 4 apart, and so on. JavaScript, whose only ordinary number type is a double, exposes the limit as `Number.MAX_SAFE_INTEGER`. A 64-bit database ID sent to a browser as a number can silently change its last digits, which is why such IDs are usually sent as strings.

### Order of operations matters

In real arithmetic, (a + b) + c equals a + (b + c). In floating point it may not, because the rounding happens at different points. Adding a very small number to a very large one can have no effect at all, since the small one falls below the large one's precision. Summing a long list from smallest to largest is more accurate than the reverse.

## Special values

The format reserves a few bit patterns for values that are not ordinary numbers.

| Value | Arises from | Behaviour |
| --- | --- | --- |
| +∞ and −∞ | overflow, or dividing a non-zero number by zero | larger or smaller than every number |
| NaN ("not a number") | 0 / 0, the square root of −1 | not equal to anything, **including itself** |
| −0 | a negative result too small to represent | equal to +0 in comparisons |

NaN is deliberately contagious: any calculation involving NaN gives NaN, so one bad value shows up at the end rather than being silently absorbed. `x != x` being true is the standard test for it.

## Why put up with this?

Because for most numerical work it is an excellent trade. Floating point is implemented directly in hardware and is extremely fast, it covers an enormous range in a fixed size, and its error is tiny *relative to the size of the number*. Measurements in science and engineering are never exact anyway.

| If you need | Use |
| --- | --- |
| Science, graphics, machine learning, statistics | floating point |
| Money | integers in the smallest unit, or a decimal type |
| Exact fractions | a rational number type |
| Counting, indexing, identifiers | integers |

## Key takeaways

- Floating point stores a sign, an exponent and a fraction, like scientific notation in base 2.
- Most decimal fractions, including 0.1, have no exact binary form and are stored as the nearest value.
- Compare floats within a tolerance, never with exact equality.
- Do not use floats for money, or for integers above 2⁵³.
- Infinity and NaN are valid values. NaN is not equal to itself.
